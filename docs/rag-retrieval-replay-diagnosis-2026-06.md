## 0. 结论先行

1. **"没召回相关数据"这个怀疑,在文档级被推翻。** 7 道失败题**全部**把 gold 文档大量召回进了 top-30,没有任何一题是"完全没找到对的文档"。问题不在"找不找得到文档",而在"**进 LLM 的 top-10 窗口里有没有那个正确段落**"。
2. **真正的失分分成两类,各占一半:**
   - **检索召回问题(段落级)** —— Q14、Q18(0420)、Q24:正确段落被挤到 top_n=10 截断线**之外**,或被**错文档的相似段**占了窗口。LLM 拿到的上下文里就没有正确答案,再强也答不对。
   - **LLM 总结问题** —— Q28、Q38、Q39:正确段落就在 top-10 **最前面**(甚至 rank1/rank2),gold 文档几乎霸榜整个窗口,LLM 却没把要点列全 / 组织错。这是生成侧,不是检索侧。
   - **边界一题** Q6:正确段落("一升一降三确保"正文)在 rank7,**进了 top-10**,但前 6 个是"风季施工难点"等干扰段,LLM 被淹没、答成了风沙难点 → 排序偏弱 + LLM 选错段的混合。
3. **两个一直误导我们的指标陷阱,这次被钉死:**
   - **假阳性**:文档级 `hit@1=1` 不代表答对。Q6 `hit@1=1`、Q14 `rank=2`,但答案都错——因为命中的是**对文档的错段落**。文档级 MRR/hit 必须降到 **chunk 级**才有意义。
   - **假阴性**:Q18(0420)、Q28(0520) 的 `matched=false` **不是没召回**,纯粹是 gold 文件名和入库文件名差几个字(`年度`vs`年`、多`资料`二字、`-打印`后缀),`normalizeDocName` 的互相包含判定没匹配上。实际 `doc_aggs` 显示召回的绝大多数 chunk 就是 gold 文档本身。**gold 文件名要对齐入库文件名,否则评测分自带噪声。**
4. **共性根因(检索侧那一半):** 两套配置都 **未启用 rerank**,且 `vectorSimilarityWeight=0.3`(即 BM25 关键词权重 0.7 主导排序),`topN=10`。纯 embedding+关键词的初排,在"同区多项目互相干扰"(顺北42 vs 顺北43)和"正文 vs 目录/封面/HSE 段落"的区分上力不从心,正确段落常被排到 10 名以外。

## 1. 排查思路:怎么想的,用了哪些诊断模式

这一节回答"**怎么思考排查的**"。结论(§0)是果,这一节是因——把模糊的"到底哪里出了问题"拆成一串**可机械执行的判别**,每一步都用一个明确的诊断模式,且每一步都落到可观测证据上,不靠猜。

### 1.1 问题定义:RAG 是两段流水线,失败必落其一

任何 RAG 回答都是一条两段流水线:

```
问题 ──▶【检索 Retrieval】──▶ top-N chunk(进 LLM 的上下文)──▶【生成 Generation/LLM】──▶ 答案
                                         ▲
                                  唯一的可观测切点
```

答案错,根因只可能在两段之一:
- **检索段错**:进 LLM 的上下文里**根本没有**正确答案所需的那段原文 → LLM 再强也变不出来。
- **生成段错**:上下文里**有**正确原文,但 LLM 没用对(漏抽要点 / 抓了干扰段 / 组织错)。

整个排查就是要在这两者之间**做一刀切分**。而切分的关键,是找到两段之间那个**唯一的观测切点 = "进入 LLM 的 top-N chunk"**。只要能 dump 出这个切点的真实内容,二分归因就成立。这也正是检索回放工具存在的理由:它就是给这个切点装的一个"探针"。

### 1.2 用到的诊断模式(逐个命名)

| # | 模式 | 通用出处 | 在本案怎么用 |
|---|---|---|---|
| M1 | **流水线二分归因 / 责任切分** | 分布式系统/编译器的 fault isolation | 在"检索→生成"的切点(top-N chunk)插探针,把"端到端答案错"二分成"检索错"还是"生成错" |
| M2 | **证据优先,拒绝从结果反推** | systematic-debugging:先复现、先取证再下结论 | 评测文档 §3 的结论全是"答案错→推测检索失败";本次先 dump 真实 chunk,把推测换成证据 |
| M3 | **加宽观测窗口(`k > topN`)** | 区分"不存在"与"被过滤" | 召回刻意取 `k=30 > 生产 topN=10`,才能看到截断线**之外**的召回——否则"正确段排第 12"会被误判成"没召回" |
| M4 | **top_n 截断线三态判别** | IR 评测的 rank/cutoff 分析 | 对每段画一条 top_n 线,正确段在**线上/线下/被错文档占据**三态,直接映射到"进没进 LLM" |
| M5 | **指标可信度审查(假阳/假阴)** | 测量前先校准仪器 | 不轻信现成的文档级 `hit@1`/`matched`;识别它对 chunk 级的假阳性、对文件名差异的假阴性 |
| M6 | **粒度下钻(文档级→chunk 级→段落级)** | 聚合指标说不通就降聚合粒度 | 评测一直停在文档级;下钻到 chunk 内容,才看见"对文档、错段落" |
| M7 | **干扰项分析(distractor analysis)** | 检索/分类的错误分析 | 看"**什么**被错排到了正确答案前面"(顺北42 表头、风季施工段),反推排序为何失灵 |
| M8 | **正交双证据交叉验证** | 三角测量 triangulation | 检索证据(召回对不对)× 答案评测(答得好不好),两个独立信号并看,才能把题钉死到检索 or 生成 |

> 这一套不是临时拼的:它对应 RAG 评测里把指标拆成 **Retrieval 质量(召回/排序)** 与 **Generation 质量(忠实度/完整度)** 两条独立轴的标准范式。M1/M2 是调试纪律,M3/M4/M5/M6 是"把检索轴量准"的手段,M7/M8 是防误判的交叉校验。

### 1.3 判别决策树(把上面的模式落成可执行流程)

对每一道失败题,严格走这棵树——这就是"逐题是怎么下结论的":

```
对失败题 Q:
│
├─① doc_aggs / gold 列:gold 文档被召回了吗?            ← M5(先排除假阴性:文件名归一是否误判)
│     │
│     ├─ 否(真没召回任何 gold 文档) ─────────▶ 【检索:文档级召回失败】(本批 0 例)
│     │
│     └─ 是(gold 文档在召回里) → 进 ②
│
├─② 回答问题所需的"正确段落",它的 rank 在 top_n 截断线之上还是之下? ← M3 加宽窗口 + M4 截断线
│     │
│     ├─ 在线下(rank > topN) ──────────────▶ 【检索:正确段被截在窗口外】(Q14 日期段、Q18 正文)
│     │
│     ├─ top_n 窗口被"错文档的相似段"占据 ───▶ 【检索:干扰项挤占窗口】(Q14 顺北42)  ← M7
│     │
│     └─ 在线上(rank ≤ topN) → 进 ③
│
└─③ 正确段在窗口里,但答案仍错? ── 对照答案评测 ──▶ 【生成:LLM 没用好】(Q28/Q38/Q39)  ← M8
                                                  └ 若正确段靠后又被前排干扰段淹没 ▶【边界:排序弱+LLM】(Q6)
```

注意 ① 这一步先做 **M5 假阴性校验**:`matched=false` 不能直接判"没召回",要先看是不是文件名归一化误判(Q18/Q28 就栽在这);确认 gold 文档真的不在召回里,才算文档级召回失败。这一层不先剥掉,后面全错。

## 2. 怎么获取召回的知识库数据(工具用法)

之前的 session 已经为此专门造了一个**只读检索回放工具**,与评测主脚本 `run.ts` 平行,零侵入。它直接调 RAGFlow `POST /api/v1/retrieval`,**完整保留每个 chunk 的原文 / 来源文档 / important_keywords / 三个相似度分**,渲染成带 `top_n` 截断线和 gold 标注的逐题 markdown——正是 §1 那个"切点探针"的实现。

```bash
cd apps/server
# 0420 KB 的失败题(文档表 Q6 / Q14 / Q18)
RAGFLOW_HOST=${RAGFLOW_HOST:-http://ragflow:9380} \
  dotenvx run --env-file=.env.eval -- \
  tsx scripts/eval/retrieval-replay.ts \
    --config scripts/eval/configs/prod-v2-topn10.json --ids 6,14,18 --k 30

# 0520 KB 的失败题(文档表 Q24 / Q28 / Q38 / Q39 → 局部 id 4 / 8 / 18 / 19)
RAGFLOW_HOST=${RAGFLOW_HOST:-http://ragflow:9380} \
  dotenvx run --env-file=.env.eval -- \
  tsx scripts/eval/retrieval-replay.ts \
    --config scripts/eval/configs/0520-baseline.json --ids 4,8,18,19 --k 30
```

- `--k 30` 刻意取 > 生产 `topN`(=10)——这就是 **M3 加宽观测窗口**:把召回窗口开到比生产截断线更大,才能区分"正确段没召回"和"正确段召回了但排在第 12"。
- 产物写到 `results/<experimentId>-replay/replay.md`。每题一节:gold 标注、文档级命中行、top-k 证据表(`# / sim / vec / term / 来源文档 / gold? / important_keywords / content 摘要`)、`top_n=10 截断线`行、`doc_aggs`(召回文档分布,直接暴露"命错文档")。
- 全局题号 → 0520 局部 id 公式:`localId = globalQ − 20`(Q24→4、Q28→8、Q38→18、Q39→19)。

**怎么读报告下结论**:严格走 §1.3 的决策树——① 看 `doc_aggs`/gold 列(并剥掉文件名假阴性)→ ② 看正确段 rank 在截断线上下 → ③ 线上仍错则交叉答案评测落到生成侧。

## 4. 关键证据(逐题摘录,标注触发了决策树哪条分支)

### Q14 顺北43 — 检索召回问题(最典型)｜分支②线下 + M7 干扰项

- **错文档干扰(M7)**:top-10 的 rank1/3/7/9/10 全是 **顺北42** 文档(`..._noimg.pdf`),其表格 caption 写着 `施工日期:2022 年03月18 日至2022年07 月02 日` —— 这正是评测文档说的"召回到错误日期段 2022-03-18~07-02"的来源。LLM 把顺北42 的日期当成了顺北43 的答案。
- **正确日期段被截在线外(分支②)**:含正确日期 `2021年10月01日至2022年01月09日` / `10月23日开始野外放样` 的 gold chunk 全部排在 **rank26、27、30**(截断线 = rank10),根本没进 LLM。
- **接收点/炮点这一半其实答对了**:gold 文档 **rank2** chunk 明确写 `接收线104条,接收点总数236928个,炮线402条,总炮数60374炮...物理点总数297302个`,在 top-10 内。
- → "日期错、数量对"的表现与召回证据完全吻合:**纯检索问题**。这题如果只看文档级 `rank=2`(M5 假阳性),会误判"检索没问题",必须下钻到 chunk(M6)才看穿。

### Q18(0420) 页岩气 — 检索召回问题(正文未进窗口)｜分支② + M5 假阴性

- gold 文档(`2014年页岩气...采集报告-打印`)确实召回了 ×16,但 top-10 召回到的是该文档的 **GPS 控制网 / HSE 管理 / 单炮对比** 等段落,以及两段**目录 TOC**(`4.2观测系统属性分析 [94]`、`3.1 束线号、桩号编排`)。真正描述"采集方法/观测系统参数 + 效果分析"的**正文段没有出现在 top-10**。
- `matched=false` 是文件名归一假阴性(`2014年度...` vs `2014年...-打印`),不是没召回——**这一步先用 M5 剥掉,否则会误判成"文档级召回失败"**。
- → LLM 在没有正确观测系统正文的情况下,只能给错误观测系统:**检索召回问题**。

### Q6 顺北21 — 边界(召回到了,但排序弱 + LLM 选错段)｜分支③边界

- 含 `通过"一升一降三确保",提升资料品质,保障次级断裂成像。(1)优化观测系统设计...` 的正文段在 **rank7**(sim=0.33),**进了 top-10**;相同内容另一份在 rank24(线外)。
- 但 top-10 的 rank1–5 全是"风季施工质量安全挑战""项目部成立""成果归档"等干扰段(M7)。LLM 被前排干扰淹没,答成了"风沙/施工难点"。
- → 正确证据进了上下文,问题在**初排把正确段排到第 7** + **LLM 没识别出它才是答案**。rerank 能直接救这题。这也是为什么它是"边界":检索把答案送进了门,但没送到最显眼的位置。

### Q28 永安 — LLM 总结问题(召回完美却没列全)｜分支③生成 + M8 交叉

- gold section **6.3「多种措施并举改善了流沙、软泥低频区域地震资料品质」正文在 rank1**;**6.3.2 采集技术对策(1)(2)(3)... 在 rank2**。永安文档占了 top-30 的 29 个 chunk。
- 召回堪称完美,答案却"缺超泥炮加密 / 单三炮组合 / 表层 Q 补偿"。这些要点就在 rank1/rank2 的段落展开里,LLM 没抽全。
- → 检索证据(rank1/2 命中)与答案评测(缺要点)两个独立信号交叉(M8),把它**钉死在生成侧**。调检索参数对它无效。

### Q38 / Q39 张集东 — LLM 总结问题｜分支③生成

- 两题 gold 文档(`张集东三采区深部三维地震勘探设计`)**几乎霸榜 top-10**(Q38 占 8/10,Q39 占 7/10),施工难点段、地质任务段召回都极充分。
- 答案却被宋工从"良好"降到"合格"(缺断层落差阈值、具体煤层编号)。召回侧无可挑剔 → **生成侧取舍/组织问题**。

## 5. 归因汇总

| 类别 | 题目 | 占比 | 该往哪修 |
|---|---|---|---|
| **检索召回问题** | Q14、Q18(0420)、Q24 | 3 / 7 | 检索参数 / rerank / chunk 切分 / metadata 过滤 |
| **LLM 总结问题** | Q28、Q38、Q39 | 3 / 7 | prompt 工程 / 更强 chat 模型 / 输出格式约束 |
| **边界(排序+LLM)** | Q6 | 1 / 7 | rerank(主)+ prompt |

> 评测文档(rag-eval-cross-standard)§3 此前把 Q14/Q28/Q38/Q39 笼统归为"真回归(检索召回退化)"。**chunk 级证据(M6)+ 双证据交叉(M8)修正了这个判断**:其中 **Q28/Q38/Q39 实际是 LLM 总结问题**(召回到位),只有 Q14 是真检索问题。这正是"文档级指标看不出、必须回放 chunk"的价值,也是这次排查最该被记住的一条。

## 6. 修复建议(按性价比排序)

1. **启用 rerank(最高优先,一举多得)。** 两套配置都没配 `rerankId`。Q6(正确段 rank7)、Q14(正确日期段 rank26)、Q18(正文未进窗口)都是"正确段落存在但初排靠后"。一个 reranker(如 bge-reranker)把语义最相关段提到前面,能同时改善这三题,且不动 chunk、不动 LLM。**⚠️ 2026-06-22 实测(见 §8)下修了这条乐观假设:rerank 只可靠压住了 Q14 的"错文档干扰",但 Q14 日期段、Q18 正文仍未进窗口,对端到端优良率提升大概率落在噪声带内。rerank 该上,但不是银弹。**
2. **修 gold 文件名对齐(消除评测噪声)。** 把题集 `reference.doc` 改成与入库文件名一致(去掉 `年度`/`资料`/`-打印`/`-noimg` 等差异),或把 `isGoldDoc` 的归一化放宽到"项目名+井号"粒度。否则 Q18/Q28 这类"召回完美却 `matched=false`"会持续误导自评分(M5 假阴性)。
3. **错文档干扰(Q14):** 同区多项目(顺北42/43/21)在向量空间高度相似。可在检索 body 里按文档 metadata(项目名/井号)做软过滤或加权,降低跨项目串台;或提高 `topN` 给正确段更多进窗口机会。
4. **关键正文段召回不到(Q18/Q24):** chunk 切分把目录 TOC 与正文割裂、关键正文段 embedding 相似度偏低。可重切 chunk、给 chunk 打领域关键词标签(项目已有的 [chunk-tagger](../apps/server/src/common/chunk-tagger/) 正是为此),提升正文段的可召回性。
5. **LLM 总结不全(Q28/Q38/Q39):** 召回到位,改 prompt —— 要求"逐条列举全部要点、不得合并省略",或对要点型问题用更强 chat 模型。**别再为这三题调检索参数,方向错了。**
6. **降评测噪声:** 固定 `temperature=0` 或每题多跑取多数,把评测文档 §4 量到的 ~6.6pp RAG 抖动压下来,否则上述改进会被噪声淹没。

## 8. 附:rerank 实测对照(2026-06-22,ssh ragflow 实跑 bge-reranker-v2-m3)

§6 第 1 条把 rerank 当成"最高优先、一举多得"的假设,这一节用真实数据检验它——结论是**收益明显低于估算**。

**环境**:评测 RAGFlow(阿里云 ECS `iZ2ze8axe2178no0glkw5xZ`,`docker-ragflow-cpu-1`,CPU-only)已挂两个可用 reranker:`BAAI/bge-reranker-v2-m3___OpenAI-API`(本地)与 `gte-rerank`(阿里云)。对 7 道失败题直接跑 baseline vs rerank 的 `POST /api/v1/retrieval`(`top_k=1024 / thr=0.2 / w=0.3 / page_size=10`=生产 topN),CPU 下每题 ~3s(**不慢,打消了 CPU reranker 拖速的顾虑**)。

| 题 | baseline gold@10 / 首排 | rerank gold@10 / 首排 | gold 密度Δ | 解读 |
|---|---|---|---|---|
| Q6 顺北21 | 6/10 r1 | 7/10 r1 | +1 | "一升一降"段两者都在窗口 |
| **Q14 顺北43** | 2/10 r2 | 5/10 r1 | **+3** | **rerank 最见效处**:压制顺北42 干扰,r1 由顺北42→顺北43;但**正确起止日期段两者都未进窗口** |
| Q18 页岩气 | 9/10 r1 | 10/10 r1 | +1 | 召回密度高但多为目录/非观测系统正文段 |

| Q28 永安 | 10/10 r1 | 10/10 r1 | 0 | 召回已饱和(LLM 题,够不着) |
| Q38 张集东难点 | 9/10 r1 | 9/10 r1 | 0 | 召回已饱和(LLM 题) |
| Q39 张集东任务 | 7/10 r1 | 10/10 r1 | +3 | gold 顶满,但本就是 LLM 题,对答案帮助有限 |

> "正确段进 top-10 窗口率"自动统计为 **6/7 → 6/7(没变)**——唯一卡住的 Q14 日期段 rerank 也没救进来。注:自动 marker 判据偏宽松(如 Q18 的"进窗口"把目录/干扰段误判成正文,是 **M5 假阳性的又一次现场复演**),故可靠看 `gold@10` 密度列,"正确段进窗"需人工复核 content。

**实测修正了哪几条估算:**
1. rerank 的**可靠收益 = 压制错文档干扰**(Q14 gold 2→5、顺北42 从 6 席降到 3 席)。这降低了"答错日期"的风险,但没把"答对日期"补上。
2. **两个真正卡住评测分的机制,rerank 都没解决**:Q14 正确日期段(只有"10月23日开始放样"、无"起止日期"字样,reranker 也判不出高相关)仍在窗口外;Q18 观测系统正文本就不在召回池(rerank 无可重排)。
3. **对已召回到位的 LLM 题(Q28/Q38)零变化**;Q24 甚至轻微负作用(gold 7→5)——印证"全局重排必须回归测全集,可能在个别题帮倒忙"。

**结论(实测版)**:rerank 低成本可上,主要价值是压跨项目干扰(Q14 类),但**对端到端优良率的提升大概率落在 ±6.6pp 噪声带内**——卡分的 Q14 日期段、Q18 正文、Q28/Q38/Q39 的 LLM 短板,它一个都没真正解决。要抬分仍须:Q14/Q18 走 chunk 重切 + 提 recall,LLM 题走 prompt/换模型。**别把 rerank 当银弹。**

**对照实验已就绪**(config 已落盘):`configs/prod-v2-topn10-rerank.json`、`configs/0520-baseline-rerank.json`。要得到端到端优良率的真数字,经 ragflow 跑答案评测对照(`run.ts` 会把 rerank 同步进 assistant 检索):
