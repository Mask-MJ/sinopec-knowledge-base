# RAG 调优台账

> 每做一次调优就在这里追加一条。目的是**让"这个数字是怎么来的"永远可追溯**，不必再从 commit、聊天记录或某个人的记忆里反推。
>
> 与 [kb-optimization-report.md](kb-optimization-report.md) 的分工：那份是阶段性**汇报**（叙事型，截至 2026-05-09，面向对外说明"我们做了什么、效果如何"）；这份是**流水台账**，一次实验一条，持续追加。历史结论仍以汇报文档为准，本文件只收录 2026-08 之后、有明确单变量对照数据的条目。

## 为什么必须记口径

同一套系统在不同尺子下能给出天差地别的数字。已经踩过的坑：宋工的严口径、我们 xlsx 的宽口径（90 分制）、不同跑批轮次三者混用，导致"优良率"数字对不上（详见 [rag-eval-cross-standard-0522-vs-0607.md](rag-eval-cross-standard-0522-vs-0607.md)）。

**所以每条记录都必须写清"哪把尺子"**：题集 + 题数 + 打分方式 + 助手 + 知识库 + 切片配置 + 模型。缺任何一项，这条记录以后就不可比，等于白记。

尤其注意两套分数不能混：

- **规则分**：答案里必须出现指定数字才算命中（`mustContain` / `mustNotContain`）。脚本自算，不需要外部模型，稳定可复现。
- **LLM judge 分**：另建一个助手当裁判，对开放题打 0~1 分，默认重复 3 次取均值。需要 `RAGFLOW_JUDGE_ASSISTANT_ID`。

**规则分和 judge 分不能直接比大小**，也不能跨题集比。

## 记录格式

    ## YYYY-MM-DD 一句话说清改了什么

    **动机**：为什么要改（触发的现象 / 问题）
    **变量**：改了哪个参数，从什么到什么。是否单变量。
    **口径**：题集 / 题数 / 打分方式 / 助手 / 知识库 / 切片 / chat 模型 / embedding / rerank
    **结果**：对照数据表
    **结论**：采纳与否，为什么
    **落地**：代码 SSOT 位置 + commit + 线上是否同步

## 2026-09-01 关闭 frequency_penalty（0.7 → 0）

**动机**：线上聊天出现回答尾部退化成乱码——引用先烂成空的 `[]`，接着雪崩成 `suite_suite__text__` / `XNUMX` / 大段 `x` 和标点，一路刷到长度上限。2026-08-30、09-01 各出现一次。

**变量**：`llm_setting.frequency_penalty` `0.7 → 0`。单变量，其余参数（`temperature=0.1` / `top_p=0.3` / `presence_penalty=0.4`）不动。

原值 0.7 是 RAGFlow 出厂"精确"档，我们建库时照抄了。它是**累加式**惩罚（`logit -= fp × 出现次数`），而长答案里 `[ID:n]` 引用和中文标点会重复几十次，被逐个罚出 `top_p=0.3` 的候选窗口后，模型只能从长尾捡 token，进入不可逆的雪崩。

**口径**：

| 项 | 值 |
| --- | --- |
| 题集 | `questions-0820.json`，32 题（dev 21 + holdout 11） |
| 打分 | 规则分 19 题参与对比；12 道 judge 题**未打分**（线上无 judge 助手） |
| 助手 | 聊天助手-0820-512-topN30（`top_n=30` / `top_k=1024` / `thr=0.2` / `vsw=0.7`） |
| 知识库 | 测试知识库-0820-512（`chunk_token_num=512` / DeepDOC / delimiter `\n`） |
| chat | `qwen3.8-max@aliyun-maas`（阿里云百炼，OpenAI 兼容） |
| embedding | `qwen3.7-text-embedding@aliyun-maas` |
| rerank | `BAAI/bge-reranker-v2-m3@siliconflow` |

**结果**：

先做单变量重放（同一助手、同一问题，只改本参数）：

|                   | fp=0.7             | fp=0      |
| ----------------- | ------------------ | --------- |
| 答案长度          | 1639 字            | 2171 字   |
| 完整 `[ID:n]`     | 22 个              | **47 个** |
| 被烧成空壳的 `[]` | **16 个**          | **0 个**  |
| 标点              | 后半段顿号句号消失 | 正常      |

再做 32 题 A/B（对照组用临时助手 `ab-fp07-temp`，跑完即删，不碰线上）：

|                     | fp=0                  | fp=0.7                |
| ------------------- | --------------------- | --------------------- |
| MRR / hit@1 / hit@3 | 0.938 / 93.8% / 93.8% | 0.938 / 93.8% / 93.8% |
| 规则分均值（19 题） | 0.873                 | 0.889                 |
| 最长答案            | 1484 字               | **43692 字**          |
| 跑挂的题            | **0**                 | **2**                 |

- 检索指标完全一致 —— 符合预期，该参数只影响生成。这也反证两轮跑批本身可比。
- 规则分低 0.016，差异只来自三题：Q4 `+0.22`（fp=0 更好）、Q12 `-0.07`、Q26 `-0.45`。**Q26 是打分假阴性**：两组答案的数字一个不差，只是 fp=0 那次用了表格排版（`| 24 |`），而规则要求数字紧跟单位（`24个`）才算命中。剔除 Q26 后 fp=0 反而略高（`+0.009`）。
- fp=0.7 组当场复现两次故障：**Q11** 刷到 43692 字（前 1300 字正常 → 泄漏英文思考独白 → 退化成同义词接龙 `extradite repatriate return restore reinstate…`，因为每个词用过就被罚，只能不停换新词）；**Q2** 跑了 5 分钟后 `fetch failed`，没拿到答案。
- 注意 **Q11 的规则分是满分 1.00** —— 前半段正常、该命中的数字都命中了。**规则分这把尺子照不出退化**，只看分数会以为一切正常。

**结论**：采纳。准确度无劣化，且消除了两类线上故障。

`presence_penalty` 保留 0.4：它是**一次性**惩罚（token 出现过就固定扣分，不随次数累加），不会雪崩。

**落地**：

- SSOT [assistant.defaults.ts](../apps/server/src/common/defaults/assistant.defaults.ts) `DEFAULT_ASSISTANT_FREQUENCY_PENALTY = 0`，附单变量对照数据注释
- 回归守护测试 [assistant.defaults.spec.ts](../apps/server/src/common/defaults/assistant.defaults.spec.ts)
- commit `b2fd250`
- 线上 14 个助手已全部改为 0，改前备份表 `dialog_bak_20260901`（16 行）

## 2026-08-31 top_n 10 → 30 并启用 rerank

> 本条数据来自 [assistant.defaults.ts](../apps/server/src/common/defaults/assistant.defaults.ts) 中该常量上方的实测记录，非本次重跑。

**变量**：`top_n` 与 `rerank_id`，两个维度交叉对照。

**口径**：0820 语料 / 32 题 / `chunk_token_num=512` / **LLM judge 同一口径**（⚠️ 与上一条的规则分**不是同一把尺子**，两者的数字不能相互比较）。

**结果**：

| 配置                    |     分数 |
| ----------------------- | -------: |
| `top_n=10`              |     62.0 |
| `top_n=20`              |     68.5 |
| `top_n=30`              |     71.7 |
| `top_n=10` + rerank     |     70.9 |
| **`top_n=30` + rerank** | **82.3** |

rerank 与 top_n 改善的是不同的题、可叠加：rerank 提 top-k 内的精度（简答 68.8→91.2、检索边界 65.0→91.2），top_n 提召回覆盖面（跨项目 5.0→38.3）。两者同开时 5 个题型全部改善，无此消彼长。

**结论**：采纳 `top_n=30` + `BAAI/bge-reranker-v2-m3`。

**落地**：`DEFAULT_ASSISTANT_TOP_N = 30`、`DEFAULT_ASSISTANT_RERANK_ID`。注意 rerank 常量**不是兜底值**——实例没挂该模型时 `resolveDefaultRerankId()` 会退到任一可用 rerank 模型，再没有就不启用。

## 2026-09-03 失分归因诊断（未改动任何配置）

**动机**：回答"准确度还能不能再优化"。在动参数之前，先搞清楚现在的分丢在哪。

**方法**：对 5 道低分题（Q9 / Q12 / Q24 / Q27 / Q32）回放 top-30 检索证据，逐个 `mustContain` 数字判定三态——**召回里有没有 / 答案里有没有**；对召回里没有的数字，再直接以该数字为 query 反查库里到底存不存在。这一步能把"检索没捞到"和"原文就没有"彻底分开。

**结果**：

| 题 | 规则分 | 必答数字 | 召回里有 | 答案里有 | 真实性质 |
| --- | --: | --: | --: | --: | --- |
| Q9 | 0.67 | 3 | 2 | 2 | 数字口径分歧，待人工核对原文 |
| Q12 | 0.47 | 15 | 8 | 7 | **题目与标准答案错配** |
| Q24 | judge | — | — | — | **检索边界题，本就无正确文档** |
| Q27 | judge | — | — | — | **检索边界题，本就无正确文档** |
| Q32 | 0.00 | 3 | 2 | 0 | **生成漏答**（多问句只答了前两问） |

逐题结论：

- **Q24 / Q27 是"检索边界"题**，参考答案就是"知识库未涉及、无明确答案"，`reference.doc` 为空 —— hit 判定必然 `rank=0`。**这两题拉低的是度量，不是能力**。剔除后，30 道有正确文档的题**全部 rank=1，hit@1 = 100%**（而不是报表上的 93.8%）。它们真正要考的是"模型会不会老实拒答"，只有 judge 能评。
- **Q12 不是检索能力问题**。缺的 7 个数字全都在库里，其中 `151061 / 113400 / 37661 / 5025 / 3.32` 还挤在同一个 chunk。没被召回是因为问题问"资料品质方面哪些指标完成得好"，而那个 chunk 讲的是"测量资料物理点总数"，语义离得远。模型答了一级品率、空炮率（切题），标准答案却要求物理点统计（不切题）。**该修的是题集，不是检索参数**。
- **Q32 是真的生成漏答**：三个桩号里有两个已经召回到了，答案一个都没写。问题是多问句（问了组合方式、推荐方案、以及在哪几个桩号铺设），模型答完前两问就收尾了。
- **Q26 的 0.45 是打分假阴性**（详见 2026-09-01 条）：答案数字一个不差，只因用表格排版 `| 24 |`、而规则要求数字紧跟单位 `24个`。

**总结论**：**继续调检索参数（top_n / 权重 / 阈值 / 切片）的收益已经很小** —— 有正确文档的题已经 100% 召回到位。剩下的失分集中在**度量口径、打分规则、题集质量、评估缺口**四处，只有 Q32 一题是模型自身该背的锅。

## 2026-09-03 修评测口径 + 补 LLM judge + 修表格排版假阴性

**动机**：执行上一条诊断给出的 A / B / C 三项。都属于**度量层**改进——不改变系统行为，只让指标反映真实水平。

**变量**：三处，互相独立：

1. `RetrievalScore` 新增 `applicable` 字段。参考文档为空的题标记为"无从评判召回"，汇总时排除出 hit@1 / hit@3 / MRR 的分母。输出会显式打印排除了几题，不偷偷改数字。
2. 新建 judge 助手 `eval-judge`（`dbedfd6c…`）：不挂知识库、`temperature=0.01`、两个 penalty 都关；id 写入 `.env.eval` 的 `RAGFLOW_JUDGE_ASSISTANT_ID`。
3. 新增 `inlineTableUnits()`：把 Markdown 表头括号里的单位补给同列的**纯数字**单元格，接在 `cleanText` 之后。

第 3 项**没有**采用"无单位就放过"的简单做法 —— `unitsCompatible('炮','')` 返回 `false` 是刻意为之，注释写明是为了修 `顺8井北` 里的 `8` 误命中 `8m` 的旧 bug。只在表格结构内补单位，边界清晰、不放宽正文匹配。

**结果**：

先用两组真实答案离线重打分，确认只修该修的、不误伤：

|                            |   旧 |       新 |
| -------------------------- | ---: | -------: |
| Q26（fp=0，表格排版）      | 0.45 | **0.91** |
| Q26（fp=0.7，bullet 排版） | 0.91 |     0.91 |
| Q9 / Q12 / Q32             |    — | 完全不变 |

全量重打分：fp=0 组 `87.9% → 90.2%`；fp=0.7 组 `84.4% → 84.4%`（该组本就没用表格）。

**这翻转了 2026-09-01 那条的一个次要结论**：当时记录"fp=0 规则分低 0.016"，实为打分 bug 造成的假象。同口径（20 题）重打分后 **fp=0 反而高 5.8pp**（90.2% vs 84.4%）。fp=0 的采纳决定不变，依据更强了。

带 judge 的完整基线（32 题，口径见 2026-09-01 条，唯一区别是打分逻辑已含本条三项改动）：

| 指标          |       改口径前 |                   改口径后 |
| ------------- | -------------: | -------------------------: |
| MRR           |          0.938 |                  **1.000** |
| hit@1 / hit@3 |  93.8% / 93.8% |            **100% / 100%** |
| 检索统计题数  |             32 | 30（2 题无参考文档已排除） |
| answer-avg    | 87.9%（20 题） |     **86.4%（32 题全评）** |
| judge-pending |             12 |                      **0** |

⚠️ `answer-avg` 前后**不可比**：改口径前只统计 20 道规则题，改口径后 12 道 judge 题也进来了（它们平均分更低，拉低了总均值）。**86.4% 才是第一个覆盖全部 32 题的数字**，往后以它为基线。

与历史 `82.3` 同样**不能直接比**：那轮的打分细节已不可考，且当时是 `fp=0.7`、打分逻辑也没有本条的三项修正。

**结论**：三项全部采纳。检索侧至此确认无优化空间（有正确文档的 30 题全部 rank=1）。

**judge 首次开出的分**，暴露了规则分完全照不出的问题：

| 题 | judge | 性质 |
| --- | --: | --- |
| Q24 | **0.10** | 该拒答却过度作答：拿"整体里程碑计划 2025年9-12月"硬凑成工期规划 |
| Q13 | **0.37** | 列举不完整：参考答案要的"四级质量检查制度"**就在 top-30 第 7 位**，召回到了却没写进答案 |
| Q18 | 0.70 | — |
| Q7 | 0.80 | — |
| Q23 | 0.90 | — |
| 其余 7 题 | 1.00 | 含 Q27（同为拒答题，干净地答了"知识库未给出，无法回答"） |

Q24 与 Q27 是同类拒答题却一个 0.10 一个 1.00 —— **模型有拒答能力，但不稳定**。

**落地**：`scoring.ts`（`applicable` + `inlineTableUnits`）、`run.ts`（汇总分母）、`scoring.spec.ts`（+7 条测试，全套 119 条通过）、`.env.eval`（judge id）。

## 2026-09-03 系统提示词补三条规则（923 → 1447 字，v6）

**动机**：补上 judge 后，剩余失分几乎全落在生成侧，且三道低分题指向三条互相独立的缺陷（见上一条诊断）。

**变量**：`DEFAULT_ASSISTANT_SYSTEM_PROMPT`。检索参数、模型、知识库全部不动。经三轮迭代定稿：

| 版本 | 改了什么 |
| --- | --- |
| v4 | ① 规则 1 补「收尾前回扫，别漏成体系的大项」② 规则 5 补拒答判据「沾边内容按未给出处理」③ 新增规则 6「多问句逐条作答」 |
| v5 | 规则 5 再补「区分知识库*说了没有* vs *压根没说*」 |
| **v6** | 规则 6 补「问题前提与知识库相悖时，先一句话点破前提，不要埋进逐条列表」 |

**口径**：与 2026-09-01 条相同，唯一区别是打分逻辑已含 09-03 的三项修正。**每个版本跑两轮**——单轮均值波动约 ±1.1pp，一轮不足以下结论。

**结果**（32 题均值，v4/v5/v6 各两轮）：

| 版本 | 均值 | 各轮 | 稳定改善 | 稳定劣化 | 净 |
| --- | --: | --- | --- | --- | --: |
| 基线 | 0.864 | 0.864 | — | — | — |
| v4 | 0.890 | 0.896 / 0.885 | Q24 +0.80、Q13 +0.13 | Q16 −0.10 | +2.6pp |
| v5 | 0.894 | 0.883 / 0.906 | Q24 +0.80、Q18 +0.20、Q13 +0.10、Q30 +0.17 | Q16 −0.20 | +3.3pp |
| **v6** | **0.897** | 0.895 / 0.898 | Q24 +0.80、Q18 +0.13、Q13 +0.03 | **无** | **+3.0pp** |

「稳定改善 / 劣化」的判据是**两轮都相对基线同向变动**，单轮出现的差异一律按噪声处理。v4 曾显示 Q18 +0.10、Q26 +0.09，第二轮即掉回，属噪声。

**Q16 是这轮的主要教训**，全历程：`基线 1.00 → v4 0.90/0.73 → v5 0.60/0.80 → v6 1.00/1.00`。

该题问"哪些障碍区使用了可控震源"，而参考答案是"本项目中未曾使用可控震源"—— **问题的前提本身不成立**。基线答得干脆（"并未使用可控震源，全区采用炸药"）。v4 的「多问句逐条作答」规则把模型带偏，强制它用"1. 是否使用了：知识库未给出…"的格式开场，把结论埋进列表、还捎带塞进大段无关的 2009 年河山项目细节。

v5 的修补方向错了 —— 去补规则 5（拒答判据），结果 Q16 更差。看答案才发现内容一直是对的，问题出在**结论的位置和措辞**，根因在规则 6 而非规则 5。v6 改对地方后一次修复。

**结论**：采纳 v6。它是三个版本里均值最高（0.897）、唯一零劣化、且两轮波动最小（0.003，v5 是 0.023）的。v5 净值虽标称更高，但那是拿 Q16 的稳定劣化换来的。

**没有做的事**：Q32 三个版本都是 0.00。多问句规则确实生效了（v6 确实逐条编号作答），但 `mustContain` 要三个桩号，模型答的是道数。这题更接近标准答案偏严——问"对比了哪几种组合方式"，答"口/吕/品三种"本身切题。**不再为单题加 prompt 规则**，那是对着测试集过拟合。

**落地**：`DEFAULT_ASSISTANT_SYSTEM_PROMPT`（923 → 1447 字）。⚠️ **只影响新建助手**；线上 14 个既有助手的 prompt 仍是 923 字旧版，需另行同步。

## 下一步优化候选

> A（检索指标口径）、B（补 LLM judge）、C（表格排版假阴性）已于 2026-09-03 完成，见上条。以下是剩余项。

### D. prompt 补强 —— 当前唯一确定的模型侧改进

补上 judge 之后，**剩余失分几乎全部落在生成侧**，而且三道低分题指向三条互相独立的缺陷：

| 题 | 分 | 缺陷 | 证据 |
| --- | --: | --- | --- |
| Q13 | 0.37 | **列举不完整** | 参考答案要的"四级质量检查制度"就在 top-30 第 **7** 位，召回到了却没写 |
| Q32 | 0.00 | **多问句漏答** | 三问只答两问；两个桩号已在召回结果里，答案一个没写 |
| Q24 | 0.10 | **该拒答却过度作答** | 拿"整体里程碑计划 2025年9-12月"硬凑工期规划；同类题 Q27 却拿了 1.00 |

现有 prompt 已有"列举类问题必须完整"和"不知道就说不知道"，但显然不够——Q13 说明"完整"没约束住，Q24 说明"沾边内容算不算知道"没界定。建议补三条：

1. 问题包含多个疑问点时逐条编号作答，任何一问查不到也要显式说明（针对 Q32）
2. 列举类问题在收尾前回扫检索结果，确认没有遗漏成体系的大项（针对 Q13）
3. 只有直接回答所问的内容才算"知识库给出了"；仅仅相关、沾边、可推测的内容一律按"未给出"处理，不要用它拼凑答案（针对 Q24）

**风险**：prompt 改动影响面大、容易顾此失彼（历史上 v2 → v3.3 反复过多轮）。第 3 条尤其要防过度拒答——把本来答得对的题也拒掉。

**做法**：现在已具备 A/B 条件（完整基线 86.4%，32 题全评，judge 就绪）。建临时助手改 prompt 跑对照，**逐题看分数变化而不只看均值**，重点盯 Q27 和其它已经满分的题有没有被拒答规则误伤。

### E. 题集勘误 —— 需要业务同事参与

- **Q12**（0.47）：问题问"资料品质方面哪些指标完成得好"，标准答案却要求列出物理点总数、复测率等测量统计。缺的 7 个数字全在库里，其中 5 个还挤在同一 chunk —— 是题目与标准答案错配，不是检索能力问题。要么改问题，要么改标准答案。
- **Q9**（0.67）：答案说金山覆盖次数 150、标准答案要 130，疑似"设计值 vs 实际值"口径差异，需核对原文。

合计约吃掉 0.9 分。**必须业务同事拍板**，不能由开发单方面改标准答案。

### 不建议做的

- **继续加大 `top_n`**：30 已让有正确文档的 30 题全部 rank=1，MRR=1.000。再加只增加上下文长度和成本。
- **调 `vector_similarity_weight`**：当前 0.7 下召回零失败，没有证据支持调整。
- **重新切片（改 `chunk_token_num`）**：至今没有发现任何一例"数字被切片切散导致召回不到"。重新入库代价大、收益无证据。

## 已知待办

- **`max_tokens` 在当前链路上是失效的**。RAGFlow `rag/llm/chat_model.py` 的 `_clean_conf()` 会 `del gen_conf["max_tokens"]`，白名单里只认 `max_completion_tokens`。也就是说我们设的 8192 从未生效，长度上限由上游默认值决定。
- **评测脚本的 `.env.eval` 里 `RAGFLOW_HOST` 仍是 `http://localhost:9380`**（历史遗留）。本机跑必须 inline 覆盖成 `http://ragflow:9380`；`package.json` 里的 `eval:*` script 已带该前缀，手敲 `tsx` 时要自己加。
